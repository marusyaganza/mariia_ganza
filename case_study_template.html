CASE FILE 001 · LANGUAGE LEARNING PLATFORM

A multi-iteration, authenticated language-learning application

Current implementation: Python/FastAPI backend with PostgreSQL, SQLAlchemy, Redis, session-based authentication, and a React client. Independently designed and built across four architectural generations.

Investigation

Problem & Scope

The platform is a private personal language-learning system designed around vocabulary review, configurable spaced repetition, and a workflow that works for short study sessions. The app is intentionally authentication-first because vocabulary, study history, and review data are personal.

The scope is not to reproduce Anki or build a public social platform. The goal is to explore a focused study workflow and use the system as a long-running engineering project across several technology generations.

The scheduling logic is a simplified implementation inspired by the Anki settings and review behavior I personally prefer. It is not a reimplementation of Anki's full algorithm.

Non-goals

  • Not a public social or community platform
  • Not a commercial or monetized product
  • Not a full reimplementation of an existing spaced-repetition algorithm

Investigation

Key Engineering Decisions

DECISION 01

Four architectural iterations as deliberate evolution

ContextThe same product domain was rebuilt across four stacks: REST/Node/React/MongoDB → GraphQL monorepo/TypeScript → Next.js/PostgreSQL/Prisma/Redis → FastAPI/PostgreSQL/SQLAlchemy/Redis (current).
ChoiceUse one consistent domain to evaluate different stacks over time rather than starting a new idea each time.
ResultA comparable body of evidence across ecosystems, and a clear technical narrative of growth.
DECISION 02

Move from a GraphQL monorepo to modular backend boundaries

ContextThe v2 monorepo held server, client, design system, and shared packages, with generated types shared across boundaries.
Trade-offShared types gave atomic changes and coordination, but coupled type generation and build tooling made independent migration harder.
ResultCurrent system uses a REST contract and modular provider interfaces instead of shared frontend/backend types.
DECISION 03

Session-based authentication over JWT

ContextPrior versions used JWT for authentication.
ChoiceMoved to server-side session state, backed by Redis.
Trade-offNeither approach is universally better — the choice changes invalidation, state ownership, cookie handling, and infrastructure requirements.

Additional decisions — backend-owned feature configuration and dictionary-provider adapters — documented in the full write-up.

Evidence

Implementation Highlights

The dictionary-provider interface defines a stable contract for lookups; each language/provider module handles API-specific parsing and normalization behind that boundary, so a provider change affects one adapter rather than the core domain.

Findings

Quality, Privacy & Constraints

The live system is intentionally not available as a public anonymous demo. Study history, vocabulary data, and account workflows are protected behind authentication. A case-study walkthrough, screenshots, architecture documentation, and selected public code provide portfolio evidence without publishing personal user data or maintaining a permanently open free-tier environment.

Verification in place

  • Unit tests for scheduling and domain logic
  • API tests for protected routes and validation
  • Selected frontend tests for critical flows
  • Static analysis, lint, and type checks
Findings

What Changed & What Comes Next

The current version intentionally favors independently deployable modules, server-owned configuration, relational data modeling, and Python backend depth over retaining every convenience of the earlier shared-type monorepo.

  • Expand selected automated tests around session auth and review scheduling
  • Document query and indexing decisions as the PostgreSQL model develops
  • Decide which stable server components, if any, to release publicly
